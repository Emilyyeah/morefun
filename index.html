1现状痛点

为什么需要这套系统

现有活动搭建流程存在系统性瓶颈，效率低、成本高、易出错

🧩

系统逻辑复杂，配置效率低

现有系统单个组件叠加了大量功能逻辑，配置项繁多且相互耦合。运营配置一个活动需在多个复杂面板间切换，理解成本高、操作链路长，效率低下。

配置效率低 · 理解门槛高
⚠️

配置易出错，排查困难

组件逻辑复杂导致配置出错概率高，参数间存在隐性依赖关系，一个配置错误可能引发连锁问题。线上出问题后，排查定位困难，修复周期长。

上线易出错 · 排查困难
🎨

美术出图切图成本高

每个功能组件都需要美术单独出图并逐一切图，运营再一个个上传配置。活动组件越多，切图量越大，美术制作成本和运营配置成本都居高不下。

美术制作成本高
🔧

系统维护成本高

过往组件逻辑层层叠加，技术债务积累严重。修改一个功能可能影响多个关联模块，日常维护和 bug 修复占用大量开发精力，挤压新功能开发空间。

开发维护成本高
🚀

新组件开发效率低

系统历史逻辑复杂、模块间耦合度高，新增一个组件需要兼顾大量存量逻辑，开发难度大、周期长。产品创新受制于系统架构，新玩法落地速度慢。

新功能开发效率低
核心症结
配置效率低 美术切图成本高 上线易出错 开发维护成本高 新组件开发效率低

4活动素材设计逻辑

美术只出一张图，其余系统自动完成

活动视觉分三层独立处理，只有头图需要美术出图，组件容器样式由系统自动生成，游戏道具图标直接调取现有资产

LAYER 1
全局氛围层
头图 — 角色立绘 + 背景 + 活动标题艺术字

每次活动差异最大的部分，决定整个活动页面的视觉调性。由美术出图，决定主色调、风格氛围。这是整个活动唯一需要美术专项制作的素材。

美术出图
每次必出
LAYER 2
组件容器层
各功能模块的背景底图 — 签到区 / 抽奖区 / 邀请区…

必须与头图风格一致（头图是暗红金色，组件容器也要暗红金色），无法独立复用。解决方案：上传头图 → Canvas 自动提取主色 → CSS 变量一键生成所有容器样式，运营零操作，系统自动完成。

为什么用 CSS 而不是 AI 生图来做容器底图？

🚫 AI 生图 — 行不通

从合并后的活动截图里裁切出各功能区域的底图，技术上不可行（图层已合并，无法分离），AI 无法做到精确裁切。

✅ CSS 渲染 — 完全够用

渐变色块、描边、发光、圆角、阴影——CSS 完全能表达这些视觉元素，只要配色对了，整体风格就对了，不需要精细纹理。

🎯 主色提取 — 足够精准

只需要提取 1 个主色，精度要求低，算法可靠。主色确定后，浅底色、深文字色、按钮色全部通过数学公式自动派生，风格始终协调。
